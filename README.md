# FileHub AIO PC for Windows

Windows 10/11용 NAS·클라우드 드라이브 마운트 프로그램입니다.

## 버전과 업데이트

- PC 버전: v1.3.108, 이후 v1.3.109 / v1.3.110...
- PC 전용 GitHub 릴리즈 태그: pc-v1.3.108 / pc-v1.3.109 ...
- Android 버전: v0.1.x — Windows 업데이트와 별개로 운영
- 프로그램 실행 시 트레이 업데이트 알림 / 환경 설정 → PC 업데이트 확인
- 새 PC 버전을 받으면 GitHub 릴리즈 ZIP SHA-256 검증 → 사용자의 설치 승인 → 원격 드라이브 안전 해제 → 프로그램 업데이트 후 재실행
- 업데이트를 강제로 설치하거나 사용자의 원격 데이터를 임의 삭제하지 않습니다.

## 설치

GitHub Releases에서 FileHub-AIO-PC-1.3.108-win-x64.zip 같은 Windows 전용 ZIP을 받습니다. 압축을 별도 폴더에 풀고 FileHubAIO.exe를 실행합니다. 기존 PC 버전에서는 업데이트 확인으로 v1.3.108을 설치할 수 있습니다.

업데이트 설치 전에는 Excel/Word 등 열린 문서를 모두 저장하고 닫아야 합니다. 안전하게 해제하지 못한 NAS 드라이브가 있으면 프로그램 교체를 중단합니다. 이전 버전은 사용자 백업 폴더에 보관합니다.

## 포함 엔진 및 출처

- .NET 10 (Windows x64 자체 포함 빌드)
- rclone v1.76.0: https://github.com/rclone/rclone
- Google 전용 rclone v1.76.0 FileHub 패치: `third_party/rclone-1.76.0-filehub-async-quota.patch`, MIT 원문 `third_party/RCLONE_LICENSE.txt`
- rclone-extra v1.76.0-extra (TeraBox): https://github.com/gulp79/rclone-extra
- WinFsp v2.1.25156 (2025 정식판, 공식 서명 MSI): https://github.com/winfsp/winfsp/releases/tag/v2.1

GitHub Actions는 공식 릴리즈 파일과 컴파일된 실행 파일의 SHA-256을 검사한 후 Windows 전체 패키지를 작성합니다. 제3자 엔진의 저작권/라이선스는 각 원본 프로젝트에 따르며, WinFsp에서 파생된 예제의 원 저작권 고지를 유지합니다.

## 소스 빌드

PowerShell에서 dotnet restore NASMount.csproj, dotnet publish NASMount.csproj -c Release -r win-x64 --self-contained true -o publish, dotnet publish LockBridge/LockBridge.csproj -c Release -r win-x64 --self-contained true -o bridge 를 순서대로 실행합니다.

두 프로젝트를 컴파일하는 것만으로 전체 배포본이 완성되는 것은 아닙니다. rclone, 확장 엔진, WinFsp 배포 파일은 GitHub Actions에서 공식 릴리즈로부터 수집합니다.

## v1.3.108 Google OAuth 전용 인증 전환 간소화

- Google Drive 30~35초 연결 지연과 공용 Google OAuth 클라이언트의
  HTTP 403 rateLimitExceeded 및 재시도가 실측됐습니다.
  API 제한을 무시하거나 재시도 횟수를 강제로 줄이지 않습니다.
- Google Drive를 정상 연결 해제한 뒤 항목의 ⋯ 메뉴에서
  Google 계정 재인증을 열면 현재 인증 방식이 공용인지 전용인지 표시됩니다.
- Google Cloud에서 다운로드한 데스크톱 앱 OAuth JSON의
  installed.client_id와 installed.client_secret을
  OAuth JSON 가져오기로 읽어 입력합니다. 웹 클라이언트 JSON과
  서비스 계정 JSON, 잘못된 Client ID는 거부합니다.
- 전용 Client ID 없이 공용 인증을 시도하려면 위험 안내에
  명시적으로 동의해야 합니다. 계정 토큰이나 Client Secret은
  애플리케이션 로그에 기록하지 않습니다.
- 새 OAuth 토큰 검증은 전체 폴더 목록을 요청하는 rclone lsf 대신
  읽기 전용 rclone about --json을 사용합니다. 개발 PC에서
  약 0.97초로 확인했고 추가적인 루트 폴더 조회를 제거했습니다.
- 검증 실패 시 기존 인증은 그대로 유지되고, 검증 성공 시에는
  이전 인증이 previous-auth.bak으로 백업됩니다.
- Google 연결 로그에 비밀정보 없이
  GOOGLE_OAUTH_CLIENT_MODE mode=shared 또는 mode=custom을 기록합니다.
- WebDAV·TeraBox, 파일 잠금, Google API pacing 100ms/Burst8,
  기존 Google VFS 캐시와 비동기 용량 처리는 변경하지 않았습니다.
- 발급 절차는 GOOGLE_OAUTH_SETUP_KR.md에서 안내합니다.
  실제 Client ID는 Google Cloud에서 사용자가 발급받아야 하며
  별도 인증을 완료하기 전에는 속도 개선이 확인됐다고 표시하지 않습니다.

## v1.3.107 WebDAV 1~2글자 이름 표시 및 Google 지연 구간 진단

- 다른 PC의 탐색기에서 WebDAV `원텍`, `오름`에
  `\\NASMount-...`가 표시되는 문제를 수정했습니다.
  기존 UNC 표시명 코드는 공유 이름이 최소 3글자일 때만
  등록을 허용했으므로 2글자 사용자 이름 전체도 누락했습니다.
  새 코드는 1~2글자 이름은 **전체 문자열 정확 일치**,
  3글자 이상의 WinFsp 축약 이름은 앞부분 일치를 허용합니다.
  현재 프로필 소유 서버 및 공유명 조건은 유지하며, 무관한
  네트워크 위치의 레지스트리를 수정하지 않습니다.
- 실제 다른 PC에서 보고된 2글자 한국어 WebDAV 예제, 기존
  문수나스 및 Google Drive 축약 이름, 다른 프로필/부분 문자열
  혼동을 방지하는 회귀 테스트를 추가하고 GitHub Actions
  릴리즈 필수 검사에도 포함했습니다.
- 2026-11-19 12:00 이후 *현재 접근할 수 있는 PC*의 로그에는
  Google 신규 연결 시도가 없었습니다. 대신 11:01:05 시작한
  Google 연결은 총 34,735ms이고, 11:01:40 루트 열람은
  349ms였습니다. 같은 날 다른 연결은 1초대부터 35초대까지
  편차가 큽니다. Google 토큰이 정상이고 VFS 캐시가 작아
  단정적인 API 또는 파일 캐시 설정 변경은 보류했습니다.
- Google rclone 프로세스 생성 시간, 첫 stderr 출력, 마운트가
  Windows 드라이브로 보이는 시간, 5/15/30/45초 체크포인트를
  개인정보와 원격 파일명 없이 안전하게 기록합니다.
  추가 연결 시 `GOOGLE_MOUNT_PROCESS_SPAWN_TIMING`,
  `GOOGLE_MOUNT_FIRST_STDERR_TIMING`,
  `GOOGLE_MOUNT_WAIT_CHECKPOINT`,
  `GOOGLE_MOUNT_DRIVE_VISIBLE_TIMING`을 비교하면
  OS 실행 지연과 rclone 내부 준비 지연을 분리할 수 있습니다.
  새로운 지연의 최종 원인과 해결 여부는 실사용 로그가 필요합니다.


## 검증 범위

업데이트 무결성, 버전 필터링, 로컬 WinFsp 저장, 백업/롤백에 대한 자동 검사를 포함합니다. 실제 사용자 NAS의 다중 PC Excel 동시 편집 및 서버별 잠금 호환성은 별도 시험이 필요합니다.

## v1.3.106 WebDAV LockBridge 네트워크 표시명 누락 수정

- GitHub Windows 빌드에서는 같은 공식 Go 소스·패치라도 실행 파일
  해시가 개발 PC와 다를 수 있습니다. 고정된 개발 PC EXE 해시로
  차단하지 않고, GitHub에서 **정확한 공식 태그·패치 적용 여부**를
  먼저 확인한 뒤 실제 빌드 결과의 독립 SHA-256 매니페스트를
  생성합니다. FileHub는 매니페스트 일치·비동기 캐시 패치 마커
  존재·일반/TeraBox 엔진과 비동일성을 모두 검증하며, 불일치 시
  기존 공식 rclone의 안전한 가상 용량 모드로 폴백합니다.

- 실제 사용자 PC에서 `새 NAS (R:)`는 **WebDAV LockBridge**
  연결입니다. rclone 백엔드는 로컬 private-mount로 실행되지만
  LockBridge의 **공개 R:은 WinFsp.Net 네트워크 드라이브**입니다.
  기존 표시명 관리 함수는 `UseLockBridge`를 제외하여 Windows의
  실제 UNC 키에 표시명 `_LabelFromReg`를 설정하지 않았습니다.
- 사용자 PC HKCU MountPoints2에서 실제로
  `##NASMount-<프로필 식별자>#새 NAS` 키가 존재하고 표시명은
  비어 있었습니다. 따라서 Explorer에
  `새 NAS(\\NASMount-...) (R:)`가 노출됐습니다.
- LockBridge 공개 드라이브도 `HasOwnedNetworkPresentation`
  검사에 포함하여 동일한 표시명·아이콘 등록을 수행합니다.
  세션별 Google/TeraBox 공유 이름과 프로필별 Bridge 이름은
  각각 자신의 WinFsp 공유만 검색하며 다른 프로그램의 레지스트리는
  건드리지 않습니다.
- WebDAV Bridge와 Google은 Shell COM의 동기 이름 변경 호출
  없이, 실제 존재하는 MountPoints2 키에만 표시명을 적용합니다.
  Windows 등록이 늦으면 30초 주기 검사에서 표시명만 재확인하며
  값이 달라진 경우에만 탐색기 갱신을 요청합니다.
- 테스트: Google/TeraBox 네트워크 공유, WebDAV Bridge 네트워크
  공유, 일반 고정 디스크·SMB 제외, 외부 네트워크 이름 불변 등
  회귀 규칙을 확인합니다.
- 실제 사용자 PC의 실행 중 v1.3.105에는 변경하지 않았으며,
  v1.3.106을 정상 종료·별도 폴더 실행해 WebDAV 표시명 및
  Google 실제 용량·TeraBox 기능 유지 여부를 후속 확인해야 합니다.

## v1.3.105 Google 전용 rclone SHA-256 검사 오연결 수정

- v1.3.104의 `RcloneExecutableInspector`가 모든 일반 엔진 및
  Google 전용 엔진을 동일한 `rclone.sha256`과 비교하는 오류 수정.
  사용자 PC에서 Google 엔진 파일은 실제로 정상
  SHA-256(`C6B2742C...`)으로 설치되어 있었으며,
  검사 프로그램만 일반 엔진의 해시(`ACD80683...`)를
  잘못 요구하여 연결을 차단했습니다. 사용자 NAS/Google
  인증이나 파일 손상이 원인이 아닙니다.
- 세 개의 엔진마다 **고유 검사 대상**을 지정합니다:
  `rclone.exe` → `rclone.sha256`,
  `rclone-terabox.exe` → `rclone-terabox.sha256`,
  `rclone-filehub-google.exe` →
  `rclone-filehub-google.sha256`.
- Google 엔진은 자체 고정 SHA-256과 별도 매니페스트 양쪽으로
  검증합니다. 빌드된 ZIP에는 새로운 Google SHA 파일을 함께
  포함하며 GitHub Actions가 이를 자동 생성·검사합니다.
- Google 전용 엔진·실제 용량 30분 캐시 구현 자체는
  v1.3.104와 동일하며 연결 실패에 직접 관련된 검사 코드만
  수정합니다. 사용자 파일·계정·설정은 변경하지 않습니다.

## v1.3.104 Google Drive 실제 용량 표시 (비동기)

- v1.3.103은 Google 원격 About API를 비활성화하므로 Windows
  탐색기에 실제 용량 대신 1PiB 가상 용량이 나타났습니다.
- 직접 읽기 전용 Google About 조회로 현재 FileHub W: 계정의
  **전체 16,106,127,360바이트(15GiB)**, 사용자 파일 등의
  사용량 및 남은 용량을 확인했습니다. RaiDrive Y:의 5TiB
  표시값은 별도 계정/요금제/연결 대상의 정보일 수 있으며
  FileHub W:의 용량으로 복사하지 않습니다.
- 새 `tools/rclone-filehub-google.exe`는 rclone **v1.76.0의
  VFS Statfs()만 한정 수정**한 별도 바이너리입니다.
  `FILEHUB_ASYNC_ABOUT=1` 환경변수에서만 실제 About을
  별도 고루틴으로 갱신하며, 탐색기의 용량 조회는 네트워크
  응답을 기다리지 않고 최근 성공한 Total/Used/Free를 즉시
  반환합니다. 성공 시 약 30분 후, 실패 시 약 30초 후
  재조회합니다. 실패하면 이전 성공값을 유지합니다.
- Google 최초 연결 직후에는 일시적으로 가상 용량이 표시될
  수 있으며, 실제 할당량이 수신되면 Windows 탐색기 알림을
  한 번 보내 표시를 갱신합니다. 탐색기 F5 시 반복적인
  Google API 호출을 발생시키지 않습니다.
- 시작할 때 별도 Google 바이너리의 SHA-256을 검증합니다.
  손상/누락이면 **기존 공식 rclone으로 자동 폴백**하고
  `--disable About` 가상 용량 모드로 작동합니다.
  검증되지 않은 바이너리에서는 동기 Google About을
  다시 활성화하지 않습니다.
- **TeraBox·WebDAV 등에는 수정된 엔진을 절대 적용하지
  않습니다.** 정식 rclone.exe, 테라 확장 엔진,
  Google VFS 읽기/쓰기 캐시, 정상 종료/업로드 보호는 유지합니다.
- 공식 Go 1.26.11 Windows/amd64, CGO_ENABLED=0,
  `go build -tags cmount -trimpath -ldflags "-s -w" -buildvcs=false`
  방식으로 제작했습니다. 수정 소스 패치와 MIT 고지를
  `third_party` 폴더에 보존했습니다.
- 검증: 원본 수정 패치 재적용, SHA-256 검증, Windows 실제
  **Q: 임시 읽기 전용 마운트**에서 첫 용량 조회 1ms,
  약 2초 뒤 실제 15GiB/약 14.99GiB 반환 0ms,
  Q: 정상 제거를 확인했습니다.
- 기존 프로그램 v1.3.103을 정상 종료한 뒤 새 ZIP을
  별도 폴더에 풀어서 연결해야 합니다. 기존 Google 인증
  및 파일은 건드리지 않습니다. 실제 W: 사용 환경에서의
  장시간 운용은 별도 최종 확인이 필요합니다.

## v1.3.103 실제 Google W: 네트워크명 및 최초 파일 읽기 지연

- 실제 사용자 PC에서 실행 중인 v1.3.102의 Google W: 네트워크
  항목을 읽기 전용으로 확인했습니다. 앱은
  `--volname "\\\\NASMount-f15d6c50-d9016a70\\Google Drive"`를
  전달하지만 Windows HKCU MountPoints2에 실제 만들어진 키는
  `##NASMount-f15d6c50-d9016a70#Goo`입니다.
- 기존 FileHub는 `#Google Drive`라는 존재하지 않는 키만 열어
  `_LabelFromReg`를 설정하려고 하므로 탐색기에
  `Goo(\\NASMount-...)`가 계속 표시됐습니다.
- 새 코드는 **실제 연결 중인 랜덤 세션 서버**와 현재 프로필명의
  접두사에 정확하게 일치하는 MountPoints2 키만 찾아 등록된
  `#Goo` 키에 `Google Drive` 표시명을 설정합니다.
  Windows가 아직 키를 만들지 않았다면 생성하지 않고 기다립니다.
  Google에는 차단 위험이 큰 Shell COM 강제 이름 변경을 적용하지
  않습니다. 다른 프로그램, 다른 세션, RaiDrive 키는 건드리지 않습니다.
- 적용·해제 시 네트워크 위치의 이름/아이콘 경로를 실제 발견된
  키로 사용하도록 일치시켰습니다. 바뀐 표시명은 Explorer의

## v1.3.94 접속 실패 즉시 강제 정리 · 종료 불가 해결 · 탐색기 가시성

  구분합니다. rclone·잠금 브리지가 실행됐다가 첫 폴더 검사 전에

- **연결 중단**을 클릭했을 때도 첫 마운트 검사 통과 전이라면
  잠금 브리지 정상 QUIT이나 연결용 세마포어를 기다리지 않고
  실패한 연결을 즉시 중단합니다. 자동 재연결은 해당 세션에서
  일시 중지되고 사용자가 명시적으로 재연결을 누르면 해제됩니다.
- **일반 프로그램 종료/상단 X**는 전체 8초 예산으로 종료합니다.
  미연결 실패 프로세스는 강제 종료하고 정상 연결은 짧게 안전
  해제를 시도합니다. 정상 연결이 응답하지 않으면 그 백엔드와
  로컬 VFS 캐시는 그대로 보존하지만 프로그램 GUI 종료 자체를
  막지 않습니다. OTA 설치만은 기존 엄격한 안전 해제 정책 유지.
- **WebDAV HTTPS**에서는 WinFsp 드라이브를 만들기 전에 TLS
  서버 인증서의 호스트명/유효기간/인증서 체인을 확인합니다.
  ormshop.iptime.org 주소로 접속했는데 NAS가
  ormshop.synology.me 인증서를 보내는 경우 연결을 시작하지
  않고 정확한 주소 수정 안내를 표시합니다. TLS 검증 우회는
  지원하지 않으며, NAS가 두 호스트 모두 쓸 경우 SAN 인증서를
  올바르게 설정해야 합니다.
- **Google Drive O:**에서 앱 내 연결 표시와 Windows 탐색기
  표시가 어긋나는 경우를 구별합니다. 약 55초 간격으로 실제
  루트 조회(6초 제한)와 Windows 탐색기 Shell 표시(4초 제한,
  독립 STA 스레드)를 확인하며, 접근 가능한 드라이브만 탐색기에
  재통지합니다. 기존 rclone, RaiDrive, 캐시를 재설정하지 않습니다.
  카드의 점 세 개 메뉴에서도 탐색기 표시를 재확인할 수 있습니다.
- 실제 회사 NAS 인증서, 탐색기 갱신 및 파일 쓰기 상태는
  회사 테스트 PC에서 최종 확인해야 합니다.

## v1.3.93 서버 기본 잠금 연결 먹통·비상 종료 개선

- WebDAV '서버 기본 잠금'은 **실험 기능**입니다. 연결을 실행하기 전에

  rclone/WinFsp 연결을 시작하지 않고 일반 파일잠금 브리지 이용을
  안내합니다. 검사 파일 삭제가 실패했다면 진단 메시지를 확인하세요.
- 서버 잠금 검사 실패 후 자동 재연결은 10분간 재시도하지 않습니다.
  실제 NAS의 LOCK 호환성은 테스트해야 하며, 오프라인 코드 검사만으로
  서버별 정상 연결을 보증하지 않습니다.
- WinFsp 가상 드라이브 존재 여부의 동기 확인을 UI 경로에서 제거하고,
  연결 중 폴더 존재 확인은 단일 백그라운드 작업으로 실행합니다.
  파일시스템 콜백이 650ms 넘게 응답하지 않으면 UI를 붙잡지 않으며,
  대기 중인 조회가 끝나기 전에는 중복 작업을 생성하지 않습니다.
- 일반 연결 해제/프로그램 종료는 기존 업로드 안전 검사를 계속 지킵니다.

  **NAS 카드 우측 점 세 개 → '비상 연결 종료 · 데이터 손실 위험'**

- **트레이 메뉴**에는 '비상 종료 · 창만 닫고 연결 보존' 및
  '비상 종료 · FileHub 연결 강제 중단' 두 경로를 추가했습니다.

  VFS 캐시·원본 파일을 확인한 뒤 재연결하세요.

  UI 종료 경로는 별도로 제공합니다. 모든 Windows 커널 상태에서

## v1.3.86 Synology 공유 폴더 다중 선택

- DSM 주소, 계정, 비밀번호를 입력한 뒤 **목록 불러오기 · 다중선택**을 누르면 DSM File Station의 SYNO.FileStation.List v2 list_share API로 현재 계정이 볼 수 있는 공유 폴더 목록을 읽습니다.
- 예: /01자료, /02자료, /video를 한 번에 체크해 저장할 수 있습니다. 저장된 폴더 목록은 NAS 연결별로 유지됩니다.
- **NAS 파일 / 폴더 탐색** 버튼으로 선택한 공유 폴더 내부를 탐색하여 파일·폴더를 선택할 수 있습니다. 탐색하는 동안 인증 세션을 재사용하므로 폴더를 열 때마다 로그인하지 않습니다.
- 공유 링크 생성·목록·해제는 체크된 공유 폴더 내부로 한정됩니다. Windows 드라이브 경로가 여러 DSM 공유 폴더 중 어디에 해당하는지 안전하게 판별할 수 없으면 추측하지 않고 DSM 파일 탐색을 안내합니다.
- 기존 v1.3.85의 단일 ShareRoot 설정은 새 ShareRoots 목록이 비어 있을 때 계속 읽습니다. 새로 선택하면 ShareRoots 목록으로 저장합니다.
- OTP 6자리 입력 방식을 유지합니다. 실제 DSM 2단계 인증 및 NAS 실기기 링크 생성은 별도 검증이 필요합니다.

## v1.3.86 시놀로지 공유 링크 오류 진단 및 신뢰 PC 인증

- 이전에는 공유 링크 생성 때마다 DSM에 새로 로그인하면서 매번 OTP를 요청했습니다.
- 이제 DSM 로그인에 첫 OTP와 함께 **이 PC 신뢰**를 선택하면 공식 enable_device_token / device_name 필드를 보내고, DSM이 반환한 did를 Windows 자격 증명 관리자에 보호 저장합니다.
- 이후 DSM 로그인에는 저장한 device_id와 device_name을 전송하므로, 서버가 신뢰를 유지하는 동안 링크 생성·목록·탐색을 반복해도 OTP를 다시 입력하지 않습니다.
- 인증이 만료·철회되거나 DSM 보안 설정이 변경되면 OTP 입력창을 다시 표시합니다. 신뢰를 해제하면 저장된 PC 기기 ID를 지웁니다. OTP 숫자는 저장하지 않습니다.
- 토큰을 NAS 주소, DSM 사용자, FileHub 연결 프로필별로 구분하므로 다른 계정이나 NAS에 전달하지 않습니다.
- 생성 대상이 비어 있으면 오류가 나기 전에 DSM 파일/폴더 탐색으로 대상을 선택하도록 안내합니다. 공유 링크 API가 거부하면 API 이름·메서드·오류 코드와 점검 항목을 표시합니다.
- 실제 DSM NAS에서 인증·기기 신뢰·링크 발급 결과는 실사용 검증이 필요합니다. Windows 컴파일 및 오프라인 정책/UI 테스트 성공은 서버 호환성의 증거가 아닙니다.

## v1.3.87 Excel 반복 저장 외부 변경 오인 방지

- WebDAV 폴더 자동감시기가 사용자의 Excel 저장으로 업로드된 파일을 외부 변경처럼 WinFsp Notify(Modified)로 다시 통보하는 원인을 루프백 WebDAV+실제 Excel 2회 저장 테스트에서 확인했습니다.
- 변경한 LockBridge는 성공한 Excel 임시파일→원본 rename의 길이와 SHA-256을 로컬 영수증으로 기록하고, 감시기가 NAS에서 읽은 파일의 크기 및 SHA-256이 일치하는 경우에만 자기 저장 알림 한 건을 제외합니다.
- 원격 파일이 다르거나 검증 실패, 알 수 없는 경로, 다른 PC의 수정/삭제는 기존 알림을 유지합니다. 다른 사용자의 실제 동시 수정을 감추기 위해 감시기 전체를 중단하지 않습니다.
- 수정 전에는 Excel 저장 직후 매번 DIRWATCH CHANGE Modified가 발생했지만, 수정 후에는 두 번 모두 OWN_SAVE_RECONCILED가 기록됐습니다. 두 저장본의 내용과 원본 서버 파일 무결성을 실제 Excel에서 확인했습니다.
- 별도 WebDAV 클라이언트 파일 생성/수정/삭제/하위폴더 변경 이벤트는 모두 검증했습니다.
- 실제 사용자의 Synology 장치/여러 PC가 동시에 편집하는 환경은 추가 확인이 필요하며, 서버 종류별 동시 저장 충돌을 완전히 해결했다고 주장하지 않습니다.

## v1.3.87 Synology 공유 링크 UI 분리

- 메인 앱의 Synology 공유 설정에는 DSM 주소/계정/저장된 암호, 2FA 신뢰, 공유 폴더 다중선택, 기본 링크 만료일과 선택적 링크 암호만 둡니다. 링크 암호와 DSM 암호 및 기기 토큰은 Windows 자격 증명 관리자에 저장하고 설정 JSON에는 보관하지 않습니다.
- Windows 탐색기 파일/폴더 우클릭 메뉴를 선택하면, 저장된 연결 프로필을 찾고 해당 파일의 DSM 경로를 매핑하여 SYNO.FileStation.Sharing.create를 자동 호출합니다.
- 성공 시 작은 창에 공유 URL과 **링크 복사** 버튼만 표시합니다. 설정창을 다시 띄우거나 링크 생성 버튼을 한 번 더 누를 필요가 없습니다.
- DSM 신뢰 기기가 만료됐다면 보안상 OTP를 다시 요구합니다. 경로나 계정 설정이 잘못됐다면 작은 창에서 설정으로 이동할 수 있습니다.
- 다중 공유 폴더 경로를 안전하게 구분할 수 없다면 임의 폴더를 선택해 공유 링크를 만들지 않습니다. 공유 링크 발급은 사용자 NAS에서 검증해야 합니다.

## v1.3.88 하단 업로드 상태 자동 갱신

- 기존에는 30초 타이머에서 선택한 NAS의 rclone VFS 업로드 상태를 조회하고, 오류나 대기 파일이 있을 때만 하단 글자를 변경했습니다. 정상 상태(업로드 대기 0/전송 0/실패 0)로 복귀해도 오래된 경고 문구가 화면에 남았습니다.
- 업로드 상태 확인은 연결 자동 재시도(30초)와 분리해 5초 간격으로 실행하며, NAS 연결 카드를 선택하면 즉시 한 번 더 조회합니다.
- 업로드 중 또는 실패 시에는 선택한 NAS 이름과 최신 상태를 표시합니다. 다시 모두 정상인 것이 확인되면 이전 업로드 경고를 자동으로 지우고 WinFsp 정상 · NAS 연결 및 파일 잠금 상태 문구로 돌립니다.
- 다른 NAS 선택 중 이전 NAS의 비동기 응답이 늦게 도착하면 그 결과를 버리고 선택된 NAS 상태를 다시 확인합니다. 한 번의 로컬 rclone RC 상태 조회가 오래 걸리는 경우 타이머 요청을 중첩하지 않습니다.
- PC 업데이트 다운로드/연결 진단 등 별도 상태 문구는 업로드 완료 이벤트가 강제로 덮어쓰지 않습니다.
- UI smoke test는 대기 1 → 0 전환, 선택 변경, 다른 상태 문구 보존, 타이머 주기를 검사합니다. 실제 사용자 PC에서 새 릴리즈 설치 후 확인이 필요합니다.

## v1.3.89 Windows 외부 라이브러리 전수 업데이트

- winfsp.net 패키지 2.1.24255에서 **2.2.26286**으로 교체했습니다.
- 포함 WinFsp MSI를 공식 **2026 Beta5 / 2.2.26286**으로 갱신하고, 릴리즈 SHA-256과 NAVIMATICS LLC의 코드 서명을 확인했습니다. 이전 Beta4의 관련 취약점 및 파일시스템/캐시 수정이 포함된 신규 베타입니다.
- SSH.NET을 **2026.0.1**로, Microsoft.Web.WebView2 SDK를 **1.0.4314.35**로 갱신했습니다. FluentFTP 55.1.0, 일반 rclone 1.76.0, TeraBox rclone-extra 1.76.0-extra는 공식 최신 확인 결과 그대로 유지했습니다.
- GitHub Actions checkout v7 및 setup-dotnet v6를 적용했습니다. .NET 런타임 타깃은 net10.0-windows로 유지하며 각 CI에서 .NET 10 최신 패치를 사용합니다.
- WinFsp 드라이버는 프로그램의 ZIP 파일로 자동 교체되지 않습니다. 사용자가 환경 설정에서 WinFsp 확인/설치를 클릭한 경우에만 버전·SHA-256을 확인하고, 연결된 FileHub NAS가 있으면 우선 안전하게 해제하도록 안내합니다. 다른 WinFsp 앱 역시 종료 후 업그레이드해야 합니다. 이전 WinFsp를 자동으로 제거하지 않습니다.
- 작업 PC에는 기존 Beta4와 기존 NAS 연결이 활성화되어 있어 새 MSI를 실제 시스템에 강제로 설치하지 않았습니다. 새 .NET 바인딩 + 기존 Beta4 조합에서 격리된 Excel 연속 저장 검증을 진행했습니다. **Beta5 MSI와 새 바인딩을 함께 설치한 실기기 검증은 배포 후 별도로 필요합니다.**

## 앞으로의 PC 소스 자동 갱신

- NuGet 라이브러리 버전은 루트의 **Directory.Packages.props**에서 중앙 관리합니다. Windows 본체와 LockBridge의 SSH.NET, FluentFTP 버전이 한 파일에서 결정됩니다.
- Dependabot이 매주 월요일(한국 시간) GitHub의 새 버전을 확인하고 PC 전용 pc/windows를 대상으로 **의존성 수정 커밋이 포함된 PR**을 생성합니다.
- PC 의존성 PR에는 별도의 Windows 빌드·정책 테스트 워크플로가 실행됩니다. 테스트 실패 시 기존 버전을 유지하며, 메이저 변경·런타임/드라이버 업데이트도 검토 후 병합합니다.
- winfsp.net은 대응 WinFsp MSI와 같은 버전/해시를 함께 검증해야 하므로 Dependabot 단독 업데이트 대상에서 제외했습니다. rclone과 TeraBox 확장도 공식 SHA-256 고정 상태를 유지합니다.
- **빌드 때마다 무조건 최신 버전을 받아 교체하거나 자동으로 정식 릴리즈를 게시하지 않습니다.** 검증된 PR을 병합한 다음 PC 앱 버전 태그를 증가시켜 전체 테스트를 통과하면 그때 새로운 Windows OTA 릴리즈로 반영합니다.
- GitHub Dependabot 설정은 GitHub가 기본 브랜치 main에서만 읽으므로, .github/dependabot.yml은 Android 소스 변경 없이 main에도 함께 설치해야 PC 자동 PR이 활성화됩니다.
